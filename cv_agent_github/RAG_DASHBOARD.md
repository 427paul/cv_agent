# 자연어 기반 데이터 검색 RAG 대시보드 (RAG Dashboard)

공공 개인사업자 평가정보 데이터를 활용하여 자연어 질의를 기반으로 정형 필터링과 비정형 의미 검색을 결합한 **하이브리드 RAG(Retrieval-Augmented Generation) 검색 대시보드** 프로젝트입니다.

---

## 🔄 3. 시스템 아키텍처 (Architecture) 및 엔드투엔드 데이터 파이프라인 (Data Pipeline 5단계)

```
[Step 01] JSON 원천 적재  ──▶  [Step 02] 서술형 청킹  ──▶  [Step 03] 임베딩 파이프라인  ──▶  [Step 04] ChromaDB 적재  ──▶  [Step 05] 검색 대시보드 배포
   (GCS & BigQuery)             (문맥화 & 메타 분리)         (128차원 & L2 정규화)           (하이브리드 색인)             (Streamlit & FastAPI)
```

1. **Step 01 · 원천 데이터 수집 및 적재**: 공공 API JSON 원본을 GCS에 아카이빙하고 BigQuery에 배치 적재
2. **Step 02 · 서술형 청킹 & 메타데이터 분리**: 코드화된 키-값 데이터를 문맥이 보존된 자연어 텍스트로 전환하고 필터용 정형 속성 분리
3. **Step 03 · 임베딩 파이프라인 구축**: 한국어 특화 `SentenceTransformers`로 128차원 벡터 변환 및 코사인 유사도 최적화를 위한 L2 정규화 적용
4. **Step 04 · ChromaDB 적재**: 정규화 벡터, 텍스트, 메타데이터를 저장하여 조건부 하이브리드 검색 인프라 완성
5. **Step 05 · 검색 대시보드 서빙 및 배포**: Streamlit 대시보드 배포 및 FastAPI를 연동한 실시간 사용자 검색 행동 로깅

## 🔍 4. 단계별 핵심 구현 상세 (Implementation Breakdown)

### STAGE 01. GCS 데이터 레이크 아카이빙
- 공공 비즈니스 평가 API의 원천 JSON 데이터를 GCS 버킷에 주기적 자동 업로드
- `hashlib` 기반 **MD5 해시 무결성 검증**을 파이프라인에 적용하여 네트워크 전송 과정 중 발생할 수 있는 데이터 손실 및 변조를 원천 차단
- Raw 데이터의 원본 불변성(Immutability)을 보장하는 데이터 레이크 아카이빙 체계 구축

### STAGE 02. BigQuery 데이터 웨어하우스 모델링 & Lineage
- 확장성 높은 분석용 정규 스키마 테이블(`biz_evaluations`)을 설계하여 데이터 배치 적재
- 적재 일시, 파일 크기, 원본 파일명, MD5 체크섬, 실행자 정보를 실시간 기록하는 메타데이터 테이블(`ingest_metadata`)을 별도 운영하여 **데이터 계보(Data Lineage)** 및 감사 추적성 확보

### STAGE 03. 서술형 시맨틱 청킹 & 메타데이터 분리
- 단순 JSON 키-값 형태로 나열된 비즈니스 코드와 지표를 LLM과 임베딩 모델이 문맥적으로 파악할 수 있는 **서술형 자연어 문장**으로 재구성
- 검색의 정확도를 보장하기 위해 필터링 조건으로 사용될 핵심 속성(지역, 성별, 연령대, 표준산업분류 업종명 등)을 **구조화된 메타데이터(Metadata)**로 분리하여 이중 색인 체계 마련

### STAGE 04. 한국어 특화 임베딩 & ChromaDB 벡터 인덱싱
- 한국어 도메인에 특화된 `SentenceTransformers` 모델을 활용하여 청킹된 문장을 **128차원 벡터**로 변환
- 벡터 간 **L2 정규화(L2 Normalization)**를 적용하여 연산량이 큰 코사인 유사도 계산을 단순 내적(Dot Product) 연산으로 대체함으로써 연산 효율 극대화
- ChromaDB 영구 컬렉션에 적재하여 고속 벡터 유사도 검색과 복합 메타데이터 필터(`where` 조건문)의 동시 실행 인프라 구현

### STAGE 05. Google Gemini 기반 지능형 Query Planner
- 비정형 자연어 질의(예: *"강릉 지역의 자동차 부품 판매업 여성 대표자"*) 수신 시, 사전 정의된 **JSON Schema**와 프롬프트 엔지니어링을 결합한 Gemini LLM 호출
- 질의의 의도를 두 가지 영역으로 자동 분해:
  - **정형 조건 (Hard Filter)**: `province`("강릉/강원"), `sex`("여"), `bzc_nm`("자동차 부품") 등 필터 매핑
  - **비정형 맥락 (Semantic Query)**: 대표자 특성, 사업 규모 등 의미 유사도 탐색용 키워드 분리
- 오탈자나 구어체 질의 속에서도 DB 필터링 파라미터를 정확하게 매핑하는 질의 계획 수립

### STAGE 06. 하이브리드 검색 엔진 & 서빙 대시보드
- **하이브리드 필터링(Hybrid Filtering)**:
  - ChromaDB `where` 조건을 통해 메타데이터에 부합하는 후보군을 1차 사전 압축
  - 좁혀진 대상군 내에서만 질의 벡터와 유사도 연산을 수행하여 불필요한 계산 배제
- **Streamlit UI**:
  - LLM이 수립한 검색 계획 요약 표시
  - 사용자가 추출된 필터를 직접 수정·보완할 수 있는 수동 필터 보정 인터페이스
  - 유사도 거리 스코어(Distance Score) 및 사업자 상세 평가 카드 시각화
- **FastAPI 비동기 로깅**:
  - `page_view`, `record_search` 등 사용자 인터랙션 로그를 비동기 HTTP 이벤트로 수집하여 운영 지표 분석 기반 마련

## ⚡ 5. 트러블슈팅 및 정량적 성과 (Troubleshooting & Impact)

### 🚨 문제 상황 (Problem / AS-IS)
전수 1:1 벡터 검색 방식 도입 시 두 가지 중대한 한계가 발생:
1. **극심한 검색 지연 (Latency Bottleneck)**:
   - 데이터가 누적됨에 따라 모든 데이터 벡터와 사용자 질의 벡터 간 1:1 전수 내적 연산을 수행하면서 쿼리 응답 시간이 최대 **20초**까지 지연
2. **필수 정형 조건 왜곡 (Condition Misalignment)**:
   - 고차원 벡터 공간의 의미 유사도에만 의존하면서 "지역(강릉)", "대표자 성별(여)" 같은 필수 정형 조건이 전체 유사도 점수에 묻혀 무시되거나 다른 데이터와 혼선 발생 (초기 테스트 정답률 **70%**)

### 💡 해결 방안 (Solution / TO-BE)
- **Gemini Query Planner + ChromaDB Hard Filter 결합 하이브리드 파이프라인**:
  - 자연어 수신 즉시 Gemini가 정형 메타데이터 조건을 분리 추출
  - 추출된 조건을 ChromaDB의 `where` 절로 먼저 전달하여 검색 후보군을 사전에 타겟팅 축소
  - 압축된 서브셋에 대해서만 벡터 유사도 연산을 적용하여 연산 부하 제거 및 정형 조건 엄격 준수

| 평가 지표 | AS-IS (전수 1:1 벡터 비교) | TO-BE (하이브리드 필터링 적용) | 성과 및 개선율 |
| :--- | :---: | :---: | :--- |
